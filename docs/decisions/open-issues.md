# 未決事項一覧

本書は optpoet の未決事項（論点）と決定を管理する正規情報源である。要件・設計・ロードマップに影響する
判断は本書へ登録し、決定後もエントリを残して来歴を保持する。関連文書は
[requirements.md](../requirements.md)、[architecture.md](../architecture.md)、
[ROADMAP](../roadmap/phase-0.md) を参照する。

## 記入規則

- 1 論点につき 1 エントリを作り、ID は `OI-NNN`（連番、再利用しない）を付ける。
- 状態は `未決 / 検討中 / 決定 / 見送り` のいずれかとする。
- 未決・検討中のエントリには必ず担当と期限を設定する（完了ゲート P0-G01）。
- 決定後も行は削除せず、状態を `決定` にして決定内容・根拠・決定日を記録する。
- MVP 影響は `必須 / 望ましい / 対象外` で分類し、MVP 境界の判断根拠にする。

## 項目定義

| 項目 | 内容 |
| --- | --- |
| ID | `OI-NNN` の一意な識別子 |
| 論点 | 決めるべき問いを一文で記述する |
| 選択肢 | 検討中の案を列挙し、各案のメリット・リスクを短く添える |
| 決定 | 採用した結論。未決時は空欄 |
| 根拠 | 決定に至った理由と却下理由 |
| MVP 影響 | `必須 / 望ましい / 対象外` |
| 担当 | 判断責任者 |
| 期限 | 決定目標日（`YYYY-MM-DD`） |
| 状態 | `未決 / 検討中 / 決定 / 見送り` |
| 決定日 | 状態を `決定` にした日（`YYYY-MM-DD`） |

## エントリ本文

### OI-001 基準日本語フォントを何にするか

- **論点**: 密度辞書と最終描画で共有する基準日本語フォントをどれにするか。
- **選択肢**:
  - 源ノ角ゴシック / 源ノ明朝（OFL-1.1）: グリフ網羅広い・多ウェイト・埋め込み/再配布明快 / ファイルサイズ大
  - IPAex系（IPA Font License 1.0）: 導入容易 / 再配布時の名称制約・実質単一ウェイト
  - OS 同梱（Yu Gothic 等）: 追加配布不要 / 版が環境で変動し NFR-02 を満たせない
- **決定**: 源ノ角ゴシック（既定・ゴシック）／源ノ明朝（選択肢・明朝）、ライセンスは SIL OFL-1.1。特定版を JP サブセットで同梱し版・ハッシュを [P1-020](../roadmap/phase-1.md) で固定。IPAex 系はフォールバック。詳細は [font-and-license.md](../environment/font-and-license.md)。
- **根拠**: OFL-1.1 が埋め込み・アウトライン化・再配布を無条件許諾し出力前検査（P5-012）を単純化。広いグリフ網羅で AC-02（暗黙代替 0 件）を満たしやすい。版固定でき NFR-02 を担保。OS 同梱は版変動、商用は費用・再配布制約で不適。
- **MVP 影響**: 必須
- **担当**: 作者
- **期限**: 2026-08-01
- **状態**: 決定
- **決定日**: 2026-07-25

### OI-002 検証用データセットの出所・ライセンス方針

- **論点**: MVP 判定用の固定検証画像 12 枚を、どの出所・ライセンスの素材から選定するか。
- **選択肢**:
  - 作者自身の撮影写真: 権利が最も単純・無条件 / 4 カテゴリ×難易度カバレッジを自前で用意する負担
  - CC0 / パブリックドメイン公開素材: カバレッジ調整が容易・帰属不要 / 実在・ライセンスの検証が必要
  - 混在（作者撮影＋CC0 補完）: 柔軟 / 権利管理が 2 系統になる
- **決定**: CC0 1.0 / Public Domain の公開素材のみを採用。主たる出所は Wikimedia Commons。CC BY 等の帰属要求ライセンスは不採用。選定結果は [validation-dataset.md](../environment/validation-dataset.md)。
- **根拠**: 帰属要求なしで来歴・出力表示の負担を避けられ、要件「権利を確認した固定写真」を満たす。カテゴリ×難易度カバレッジを既存素材から調整でき、第三者が同一データで再現可能（P0-G03）。ライセンステンプレートを MediaWiki API で実データ確認済み。
- **MVP 影響**: 必須
- **担当**: 作者
- **期限**: 2026-08-01
- **状態**: 決定
- **決定日**: 2026-07-25

### OI-003 AC-03 の密度 MAE をどの尺度で判定するか

- **論点**: AC-03 の合否に使う密度 MAE を、実レンダリング PNG の画素領域と、密度辞書の正規化密度領域のどちらで測るか。
- **選択肢**:
  - 案A: 辞書正規化密度 MAE を判定値にする — 最適化の目的関数と一致し改善が数値へ表れる / 実画面の見え方と直結しない
  - 案B: 実レンダリング MAE（画素領域）のまま閾値を測定尺度に合わせて下げる — 実画面と直結 / 閾値の根拠が経験値になり、改善の良否を表さない
  - 案C: 両者を独立の受入条件にする — 情報は最大 / 条件が増え判定が複雑化する
- **決定**: 案A。AC-03 の判定値を辞書正規化密度 MAE（`optpoet.text.evaluate.evaluate_layout` の `mae`）とする。実レンダリング MAE（[evaluation-metrics.md](../environment/evaluation-metrics.md) 3章の画素領域）は補助指標として記録を続け、合否には用いない。判定値の正規化条件（`dictionary_id`、フォント、描画設定、`min_ratio` / `max_ratio`）を測定ごとに記録し、辞書が違う測定値を同列比較しない。
- **根拠**: P1 完了ゲートの実測（[phase-1-gate.md](../environment/phase-1-gate.md)）で、文字の黒画素率が 0.000〜0.153 に限られる一方、目標密度は 0.0〜1.0 を使うことが確認された。密度だけで自由に文字を選ぶ基準配置（P1-034）でも画素領域 MAE は 0.5145 までしか下がらず、文字選択の良否が画素領域の改善率にほとんど表れない。同じ配置を密度領域で測ると MAE 0.0003 となり、最適化の性能差が判定へ反映される。案B は閾値が尺度の構造的上限に張り付き、案C は AC の数を増やして判定を複雑にする。
- **MVP 影響**: 必須
- **担当**: 作者
- **期限**: 2026-08-10
- **状態**: 決定
- **決定日**: 2026-08-10
- **来歴**: 2026-08-10 反映。[quality-and-operations.md](../quality-and-operations.md) 7章（AC-03 の判定値）、
  [evaluation-metrics.md](../environment/evaluation-metrics.md) 3章（3.1 密度領域＝判定値 / 3.2 画素領域＝補助、
  正規化条件の記録）、[acceptance-record.md](../environment/acceptance-record.md)（AC-03 の記録様式）、
  `src/optpoet/render/metrics.py`・`tests/test_render_metrics.py`・`tests/test_text_evaluate.py`（指標の位置づけ）、
  `gates/p1/run_gate.py`（判定値を密度領域へ、正規化条件を出力へ記録）。
  正規化の契約は既存テスト `test_density_table_spans_zero_to_one` が担保する。

### OI-004 AC-03 の 20% 判定をどのフェーズの完了ゲートで課すか

- **論点**: AC-03 の「改善率中央値 20% 以上」を Phase 1 の完了ゲート P1-G02 で課すか、Phase 2 へ送るか。
- **選択肢**:
  - 案A: P1-G02 で 20% を課し続ける — 基準が一貫 / Phase 1 の置換候補では原理的に到達できず Phase 1 が終わらない
  - 案B: P1-G02 は測定・記録で合格とし、20% は P2-G01 で判定する — 段階に見合う判定 / 判定の空白期間ができる
  - 案C: Phase 1 へ形態素解析ベースの言い換えを前倒しする — 早期に 20% へ近づく / Phase 2 の主要範囲を Phase 1 に持ち込み、フェーズ境界が崩れる
- **決定**: 案B。P1-G02 の合格条件から 20% を外し、「両尺度の MAE・改善率・除外枚数・探索記録を測定し保存できること」に変更する。20% の判定は AC-01〜AC-07 を対象とする [P2-G01](../roadmap/phase-2.md) で行う。旧条件での 1.21% は不合格として実行記録に残し、新条件で過去結果を合格へ書き換えない。
- **根拠**: Phase 1 の置換候補は表記置換（かな⇔カナ、約物、空白）に限られ、実測で 2 反復・採用 311〜412 件／2,000 セルで収束する。意味を保つ言い換えは形態素解析（P2-023 / P2-024）を前提とするため、20% は Phase 2 の候補生成が入って初めて評価できる。案C はフェーズ依存関係を壊し、Phase 1 の完了を先送りする。
- **MVP 影響**: 必須
- **担当**: 作者
- **期限**: 2026-08-10
- **状態**: 決定
- **決定日**: 2026-08-10
- **来歴**: 2026-08-10 反映。[phase-1.md](../roadmap/phase-1.md) P1-G02（条件を測定・記録へ変更、合格）、
  [phase-2.md](../roadmap/phase-2.md) P2-G01（20% 判定の実施先を明記）、

### OI-005 50MP を超える検証画像 architecture-2 をどう扱うか

- **論点**: 検証データセットの architecture-2（50,291,940 px）が FR-01 の受入上限 50MP を超え、通常経路で受け入れられない問題をどう解くか。
- **選択肢**:
  - 案A: FR-01 の上限を引き上げる — 原本を維持できる / 受入上限という要件を検証データの都合で動かすことになる
  - 案B: 縮小した副本を標準入力として使う — 差し替え不要 / 検証データセットが「原本ハッシュで固定」でなくなり、再現条件が曖昧になる
  - 案C: 50MP 未満の原本へ差し替え、超過原本は異常系テスト用に残す — 受入上限と検証データの両方を保てる / 画像 1 枚の再選定が必要
- **決定**: 案C。FR-01 の 50MP / 100MB 制限は維持する。architecture-2 の枠には、カテゴリ（建築）・難易度・権利条件（CC0 / PD）を保った 50MP 未満の原本を採用する。50,291,940 px の原本は AC-06 の上限超過ケース用として [validation-dataset.md](../environment/validation-dataset.md) に残し、通常の 12 枚セットからは外す。
- **根拠**: 受入上限は FR-01 の要件そのもので、検証データの都合で動かす対象ではない（案A 却下）。案B は黙って縮小した副本が標準入力になり、[validation-dataset.md](../environment/validation-dataset.md) の原本ハッシュ固定と AC-03 の再現性を損なう。案C は差し替え 1 枚の作業で両方を満たし、超過原本は異常系の実データとして価値が残る。
- **MVP 影響**: 必須
