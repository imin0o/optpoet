# 秘密情報の非保存とスキーマテストによる保証

**状態**: 定義済み（2026-07-25）。秘密情報の定義・検査範囲・検出規則・テスト集合・実行タイミングを確定する。テストフレームワークと具体実装、エントロピー閾値の実測、提供者別キー書式は Phase 1 実装で確定する。
**目的**: [project-manifest.md](project-manifest.md) の不変条件 **I-06（秘密情報不在）** を、開発中に自動で破れないよう機械検証する仕組みを固定する。NFR-08「API キーや不要な本文をログへ出さない」と[quality-and-operations.md](../quality-and-operations.md)「API キーは OS の資格情報保管または環境変数で扱い、プロジェクト、ログ、出力へ保存しない」を、テストで落とせる基準まで具体化する。
**対象タスク**: [P0-043](../roadmap/phase-0.md)
**関連**: [project-manifest.md](project-manifest.md)（I-06 / I-07、必須ブロック）、[artifact-storage.md](artifact-storage.md)（ディレクトリ構成・ハッシュ表記）、[provenance-format.md](provenance-format.md)（7 章「秘密情報とマスク」）、[ai-adapter-contract.md](ai-adapter-contract.md)（要求・応答エンベロープ）、[ai-failure-responses.md](ai-failure-responses.md)（F-AUTH 応答）、[requirements.md](../requirements.md)（FR-17 / FR-18）、[quality-and-operations.md](../quality-and-operations.md)（NFR-08、AC-05 / AC-06）、[change-management.md](change-management.md)

## 原則

- **保証は二層**。第一に「そもそも保存しない」構造（許可リスト方式のスキーマ）、第二に「混入していないことの検査」（値パターン走査）。検査だけに頼らない。
- **拒否リストを主にしない**。秘密情報の名前と書式は予測しきれないため、**既知キーのみ許可**するスキーマを主たる保証とし、値パターンは補助とする。
- **テストは網羅的な機密検出器ではなく、I-06 の回帰防止**である。目的は「実装変更で秘密が保存物へ入り始めたことを、その変更のテストで落とす」こと。
- **除外（allowlist）はパス単位・理由付きでのみ許す**。規則そのものの無効化は禁止する。
- 検出時は**保存・エクスポートを中止**し、部分的に書いた実体を残さない（[P0-044](../roadmap/phase-0.md) の原子的保存と連動）。

## 1. 秘密情報の定義

| ID | 分類 | 例 |
| --- | --- | --- |
| S-01 | API キー・アクセストークン | 提供者発行のキー、`Bearer` トークン、リフレッシュトークン |
| S-02 | 認証ヘッダ | `Authorization`、`X-Api-Key`、`Cookie` / `Set-Cookie` |
| S-03 | URL 埋め込み資格情報 | `https://<user>:<pass>@host/...` |
| S-04 | 秘密鍵・証明書 | PEM ブロック、鍵ファイルの内容 |
| S-05 | 端末固有情報 | 絶対パス、OS ユーザー名、ホスト名、端末識別子 |
| S-06 | 提供者内部識別子 | 応答に含まれるアカウント ID・組織 ID・課金 ID |

- S-05 は厳密には秘密ではないが、プロジェクトの可搬性（I-07）と作者の匿名性を損なうため同じ検査で扱う。
- S-06 は `provenance` に必要な `model_id` / `token_usage` を除き保存しない（[provenance-format.md](provenance-format.md)）。
- **保存物に残してよいのは、資格情報の値でも所在でもない**。MVP は単一作者・固定の環境変数名で運用するため、環境変数名やキーの保管場所すら manifest へ書かない。

## 2. 検査範囲

プロジェクトルート（[artifact-storage.md](artifact-storage.md) のディレクトリ構成）全体を対象とする。

| 対象 | 走査方法 |
| --- | --- |
| `manifest.json` | 構造走査（層 A＋層 B） |
| `ai/requests/` `ai/responses/` `ai/prompts/` | 構造走査（層 A＋層 B） |
| `text/` `trace/` `outputs/*.txt` | 全文走査（層 B） |
| `index.sqlite` | 全テキスト列を走査（層 B）。派生物だが配布されうる |
| `.tmp/` 残留物 | 全文走査（層 B）。空であることも確認 |
| アプリログ | 全文走査（層 B）＋本文非出力の確認（T-07） |
| `input/` `derived/` `outputs/*.png` | 既定では走査しない（バイナリ）。ただし画像メタデータ（EXIF / XMP）の残存テキストは走査する |

- フォントファイルは対象外（作者が導入した第三者資産であり、生成物ではない）。

## 3. 層 A: 構造的保証（許可リスト方式）

manifest・要求／応答エンベロープ・プロンプト記録の各スキーマを **既知キーのみ許可**（未知キーを拒否）として定義する。

- **D-01 未知キー禁止**: スキーマに定義のないキーが現れたら失敗。提供者応答をそのまま保存せず、アダプターが既知キーへ写して保存する契約（[ai-adapter-contract.md](ai-adapter-contract.md) X-01）を機械的に強制する。
- **D-02 禁止キー名**: 万一スキーマが緩められた場合に備え、キー名の拒否リストも併用する。`api_key` / `apikey` / `authorization` / `auth` / `token` / `access_token` / `refresh_token` / `secret` / `password` / `credential` / `bearer` / `x-api-key` / `cookie` / `session`。比較は小文字化し `-` `_` を除去した正規形で行う。
- 層 A は**保存時にも実行する**（後述 5 章）。走査が軽く、NFR-04 の保存時間へ影響しないため。

## 4. 層 B: 値パターン検査

層 A を通過した「既知フィールドの値」に秘密が混入する経路を検査する。

| ID | 規則 |
| --- | --- |
| D-03 | 資格情報書式: `Bearer <値>`、提供者プレフィックス付きキー、JWT（`.` 区切り 3 部の base64url）、`-----BEGIN ... PRIVATE KEY-----` |
| D-04 | URL 埋め込み資格情報: `://<user>:<pass>@` を含む文字列 |
| D-05 | 高エントロピー文字列: 長さ 32 以上、base64 / hex 文字集合、Shannon エントロピーが閾値以上 |
| D-06 | 端末固有情報: 絶対パス（`C:\`、`/home/`、`/Users/`、UNC）、OS ユーザー名、ホスト名 |
| D-07 | カナリア一致: テスト実行時に環境へ注入した既知のダミー資格情報値との完全一致（次章 T-02） |

- **D-05 の誤検出対策**: ハッシュ値は正当に高エントロピーである。`sha256:` 前置の値、`ref.hash`、`request_hash` / `prompt_hash` / `cache_key`、および内容アドレス由来のファイル名（16 桁 16 進）は**位置指定の allowlist** で除外する。パターン単位で D-05 を無効化しない。
- **D-06 の適用範囲**: `path` は I-07 で既に相対パス必須。D-06 はそれ以外の任意テキスト（作者メモ `note`、素材の出典、ログ）へ適用する。

## 5. テスト集合

| ID | 内容 | 合格条件 |
| --- | --- | --- |
| T-01 | スキーマ検証: 正常な manifest・エンベロープ・プロンプト記録を層 A で検証 | すべて通過 |
| T-02 | **カナリア注入**: 環境変数へ既知のダミー資格情報を設定し、モック経路で 1 作品を通し（`analyze_image` → `draft` → `paraphrase` → `optimize` → `render` → 保存）、保存後にプロジェクトルート全体をその値で走査 | ヒット 0 件 |
| T-03 | パターン走査: 保存物全体へ D-02〜D-06 を適用 | 検出 0 件 |
| T-04 | **負の対照**: 秘密を意図的に含む fixture を検査器へ通す | 分類ごとに必ず検出される（検出器の破損・無効化を検知） |
| T-05 | 失敗応答: F-AUTH を含む 4 失敗クラスの応答を保存し走査（[ai-failure-responses.md](ai-failure-responses.md)） | 検出 0 件。提供者エラー本文にキー断片が混じっても保存されない |
| T-06 | エクスポート: 共有用エクスポート出力へ層 A＋層 B を適用 | 検出 0 件 |
| T-07 | ログ: 1 作品分の工程ログを走査し、`call_id` / `seq` / 工程 ID / 所要時間 / 失敗クラス / ハッシュ先頭以外の本文が出ないことを確認 | プロンプト本文・生成文章本文・画像・秘密情報のいずれも不在 |
| T-08 | 未知キー拒否: manifest へ `api_key` および未定義キーを注入 | 保存・読込が明示エラーで失敗する |

- **T-02 が本命**。実キーを使わず、ダミー値の完全一致で「実装が資格情報をどこかへ書いたか」を確実に判定できる。正規表現の網羅性に依存しない。
- **T-04 がなければ T-02 / T-03 の合格は無意味**（検出器が常に 0 件を返すだけで通る）。両者は常に対で維持する。

## 6. 実行タイミング

| 契機 | 実行する層 | 失敗時の挙動 |
| --- | --- | --- |
| 保存（プロジェクト書込み） | 層 A のみ | 保存を中止し、`.tmp/` を破棄。作者へ明示エラー（[P0-044](../roadmap/phase-0.md)） |
| エクスポート | 層 A＋層 B | エクスポートを中止。部分ファイルを残さない |
| 開発時テスト（毎回） | T-01〜T-08 | テスト失敗 |

- 層 B の全走査は保存ごとには実行しない（大きな `text/` `trace/` を毎回走査すると NFR-04 の保存時間を圧迫するため）。開発時テストとエクスポート時に限定する。

## 7. 誤検出と例外の扱い

- 例外は `{パス, 規則 ID, 理由}` を持つ **allowlist エントリ**としてのみ登録する。ワイルドカードによる広域除外と、規則そのものの無効化は禁止する。
- allowlist の追加は [change-management.md](change-management.md) の手順で扱い、追加理由を記録する。
- 検出が誤検出だった場合でも、まず「その値を保存しない設計に変えられるか」を検討し、変えられない場合のみ allowlist へ追加する。

## 突合（要件との整合）

| 要件 | 本書での担保 |
| --- | --- |
| I-06 秘密情報不在 | 層 A（未知キー拒否）＋層 B（値走査）＋T-02 カナリアで機械検証 |
| I-07 相対パス | D-06 で保存物全体の絶対パス・端末固有情報も検査 |
| NFR-08 可観測性 | T-07 でログ出力項目を検証し、本文・キーの非出力を保証 |
| FR-17 プロジェクト保存 | 保存時に層 A を必須化し、来歴を保ちつつ秘密を排除 |
| FR-18 明示送信 | 資格情報の所在を保存しないため、プロジェクト配布で意図しない送信経路が復元されない |
| AC-05 保存 | 検査失敗時は保存中止・部分書込みなしとし、保存物の一貫性を維持 |
| AC-06 異常系 | T-05 で F-AUTH を含む失敗応答保存時の秘密混入を検証 |

- T-02 のカナリアが、モック経路だけでなく実呼出経路でも同じ保存パスを通ることの確認（経路差で検査が素通りしないか）。

- 画像 EXIF / XMP に作者名・端末情報が残る場合、正規化工程（`normalize`）で除去されているかの実測確認。
