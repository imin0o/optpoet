# 中間生成物のファイル配置・内容ハッシュ・キャッシュキー

**状態**: 定義済み（2026-07-25）。プロジェクトのディレクトリ構成、内容ハッシュの算出規則、工程別キャッシュキーと無効化規則を確定する。原子的保存の手順と読取専用オープンは [P0-044](../roadmap/phase-0.md)、来歴の詳細形式は [P0-042](../roadmap/phase-0.md) で確定する。
**目的**: [project-manifest.md](project-manifest.md) が論理形のみ固定した ref（`path` / `hash` / `media_type`）に**物理的な意味**を与える。同一入力・同一設定で同じ中間生成物を再利用でき（NFR-05）、閉じて再読込しても実体を失わず（NFR-06）、保存応答からの再生でハッシュ一致を判定できる（AC-04 / AC-05）状態を作る。
**対象タスク**: [P0-041](../roadmap/phase-0.md)

## 原則

- **プロジェクトは自己完結**: 再読込・再生に必要な実体はすべてプロジェクトディレクトリ内に置く。外部の共有キャッシュは**高速化のための複製**に限り、消えても再構築で復旧できる（NFR-06）。
- **参照は相対 POSIX パス**: manifest の `path` はプロジェクトルートからの相対パスで、区切りは `/` 固定。Windows でも `\` を保存しない（[project-manifest.md](project-manifest.md) I-07）。
- **キャッシュキーで配置し、上書きしない**: 中間生成物のファイル名はキャッシュキーから決まる。入力または設定が変われば別ファイルになり、既存実体を破壊しない。
- **無効化は依存グラフで伝播**: 前段が変われば後段のキーが変わる。無関係な中間生成物はそのまま再利用する（[architecture.md](../architecture.md)）。
- **秘密情報を実体へ書かない**: 要求・応答・プロンプトの保存時に資格情報を除去する（[P0-043](../roadmap/phase-0.md)、NFR-08）。

## ディレクトリ構成

プロジェクトは 1 ディレクトリ（以下「プロジェクトルート」）を単位とする。

```
<project-root>/
  manifest.json            # 正規情報源（project manifest）
  index.sqlite             # 索引・履歴・評価（manifest から再構築可能な派生）
  input/                   # 原本画像（作者が読み込んだファイルの複製）
  derived/
    normalized/            # 正規化後画像（EXIF / ICC / 透過）
    preprocessed/          # 前処理後画像
    density/               # 密度マップ・エッジ補助結果
    dictionary/            # 文字密度辞書（正本）
  ai/
    requests/              # 要求エンベロープ
    responses/             # 応答エンベロープ
    prompts/               # 送信プロンプト本文（P0-042）
  text/                    # 草稿・素材・言い換え候補・最終文章
  trace/                   # 探索履歴・評価中間値
  outputs/                 # 最終 PNG / UTF-8 TXT
  .tmp/                    # 書込み中の一時ファイル（同一ボリューム、P0-044）
```

- `input/` は原本を**複製して保持**する。原本の外部パスに依存すると移動・削除で再生不能になるため（NFR-06）。原本の元パスは記録のみとし、再読込では参照しない。
- `index.sqlite` は manifest から再構築できる派生物とし、欠落・破損時は manifest から作り直す。索引を正とみなさない。
- `.tmp/` は保存完了時に空にする。残留物は次回起動時に破棄する。

## ファイル命名

| 対象 | 命名 | 例 |
| --- | --- | --- |
| 中間生成物 | `<cache_key の先頭 16 桁>.<ext>` | `derived/density/9f2c4ab1d07e3355.npy` |
| AI 要求 | `<request_hash の先頭 16 桁>.req.json` | `ai/requests/3b81aa50c6f4d219.req.json` |
| AI 応答 | `<request_hash の先頭 16 桁>.a<試行連番>.res.json` | `ai/responses/3b81aa50c6f4d219.a1.res.json` |
| 出力 | 固定名 | `outputs/artwork.png` / `outputs/artwork.txt` |
| manifest | 固定名 | `manifest.json` |

- 応答のみ試行連番（`a1` / `a2` …）を付ける。同一要求が失敗後に再試行で成功した場合、`request_hash` は同一でも応答実体は複数あり、連番なしでは後続応答が失敗応答を上書きするため（失敗も履歴として保持する、[provenance-format.md](provenance-format.md)）。連番は `ai_calls` の `seq` 昇順に採番し、既存応答を書き換えない。
- 先頭 16 桁（64 bit）は同一プロジェクト内の衝突回避に十分とし、完全なハッシュは manifest の `hash` に保持する。読込時は `hash` を正として照合する（先頭桁は配置のためだけに使う）。
- 出力のみ固定名とする。作者が直接扱うファイルであり、内容の同一性は manifest の `hash` で判定するため（AC-04）。

## 内容ハッシュ

| 項目 | 決定 |
| --- | --- |
| アルゴリズム | SHA-256 |
| 表記 | `sha256:<64 桁の小文字 16 進>`（アルゴリズム識別子を必ず前置し、将来の変更を検出可能にする） |
| 対象 | ファイルのバイト列そのもの（メタデータ・タイムスタンプを含めない） |
| 選定理由 | Python 標準 `hashlib` で追加依存なく、参照環境（Windows 11 x64）で十分な速度。作品制作用途であり暗号学的攻撃モデルを想定しない |

### 構造化データの正規化（ハッシュ前）

JSON など構造化実体は、ハッシュ前に次を満たす正規形へ直列化する。同一内容が異なるバイト列になるとキャッシュが不当に無効化されるため。

- キーは Unicode コードポイント昇順、UTF-8（BOM なし）、改行 LF、インデントなし、キー・値の区切りに余分な空白を置かない。
- 浮動小数は固定桁で丸めてから文字列化する（丸め桁は工程ごとに定義し、値と同じ場所に記録する）。`-0.0` は `0.0` へ正規化する。
- 既定値の項目を省略しない。省略と明示的な既定値を別扱いにしない。
- 配列の順序は意味を持つものとして保持し、勝手に整列しない。
- 生成時刻・実行ホスト・所要時間などの**実行環境依存値はハッシュ対象へ含めない**（記録は別項目で行う）。

### 画像・バイナリ

- 密度マップ・画像は保存形式を工程ごとに固定し、そのバイト列をハッシュする。可逆形式のみ使う（非可逆圧縮は再生一致を壊す）。
- PNG は生成時刻等の可変チャンクを書き込まない。書き込む場合はハッシュ対象から除外せず、**そもそも書かない**方針とする（AC-04 のバイト比較を単純に保つ）。

## キャッシュキー

キャッシュキーは「その中間生成物を一意に決める入力集合」のハッシュとする。

```
cache_key = sha256( canonical_json({
  "stage": <工程 ID>,
  "stage_version": <工程実装の版>,
  "inputs": [<依存する実体の hash（順序固定）>],
  "params": <当該工程の正規化済みパラメータ>
}) )
```

- `stage_version` は工程の実装が変わって出力が変わりうるとき上げる。上げ忘れると古い実体が誤って再利用されるため、変更管理は [change-management.md](change-management.md) に従う。
- `inputs` には**直前段の実体ハッシュのみ**を入れる。前段のキーが変われば前段の実体ハッシュが変わり、後段キーへ自動的に伝播する。
- `params` は工程が実際に読む値だけを含める。無関係な設定変更で再計算しないため（NFR-04 / NFR-05）。

### 工程別のキー構成

| 工程 ID | `inputs` | `params`（主要） | 出力先 |
| --- | --- | --- | --- |
| `normalize` | 原本画像 | EXIF Orientation / ICC / 透過の扱い | `derived/normalized/` |
| `preprocess` | 正規化後画像 | crop / rotate / brightness / contrast / gamma / invert | `derived/preprocessed/` |
| `density_map` | 前処理後画像 | 手法・ガンマ・局所コントラスト・エッジ重み・`grid.cols` / `rows` / `cell_aspect` | `derived/density/` |
| `edge_map` | 前処理後画像 | エッジ抽出手法とパラメータ | `derived/density/` |
| `dictionary` | フォントファイルのハッシュ | 文字集合・サイズ・ウェイト・描画設定・描画エンジン版 | `derived/dictionary/` |
| `ai_call` | （なし。`request_hash` を使う） | — | `ai/requests/`・`ai/responses/` |
| `optimize` | 密度マップ・辞書・草稿／候補 | 重み・許容差・反復上限・シード・探索方式と版・固定箇所 | `text/`・`trace/` |
| `render` | 最終文章・辞書 | グリッド・描画設定・文字色／背景色 | `outputs/` |

- `dictionary` のキーは manifest の `fonts.dictionary_id` と同一の入力集合から導出する（FR-04 のキー定義）。フォントを差し替えればファイルハッシュが変わり、辞書も別実体になる（NFR-02）。
- `ai_call` はキャッシュキーを別途持たず、[ai-adapter-contract.md](ai-adapter-contract.md) の `request_hash`（`payload`＋`params`＋`model_id`）をそのまま配置キー・照合キーとする。同一要求は同一保存応答へ確定的に対応する（X-02）。
- `render` の出力は固定名だが、キーは manifest の `outputs.*.hash` と `render_metadata` で追跡する。

### 再利用と無効化

- 工程実行前にキーを算出し、該当ファイルが存在して `hash` が一致すれば**再計算せず再利用**する（NFR-05 中断耐性）。
- 前段が変わった場合、後段のキーが変わるため自動的に再計算対象になる。無関係な工程の実体は残り、再利用される（[architecture.md](../architecture.md)）。
- 不一致（ファイルはあるが `hash` が合わない）は**破損として報告**し、暗黙に再生成しない（[project-manifest.md](project-manifest.md) I-02）。作者の明示操作で再生成する。
- 参照されなくなった実体は自動削除しない。中断・取消後の再開で必要になりうるため、削除は作者の明示操作（整理コマンド）に限る。削除対象は「現行 manifest と編集履歴のどちらからも参照されない実体」とする。

## 共有キャッシュ（任意・高速化のみ）

文字密度辞書はプロジェクト横断で同一になりうるため、ユーザー領域（`%LOCALAPPDATA%` 配下）に複製を置いてよい。ただし次を守る。

- プロジェクト内 `derived/dictionary/` を**正本**とし、共有キャッシュはその複製とする。共有キャッシュだけに存在する状態を作らない。
- 共有キャッシュのヒット判定は `dictionary` のキャッシュキー完全一致に限る。部分一致・近似での再利用をしない。
- 共有キャッシュが欠落・破損しても、プロジェクト内の正本から復旧し、正本もなければ再測定する。共有キャッシュの有無で結果が変わらないこと（NFR-01）。
- 共有キャッシュへ入力画像・文章・AI 応答を置かない。プロジェクト固有データを端末共有領域へ出さない（NFR-08）。

## 再確認事項（実装時に更新）

- 5,000 セル作品でのプロジェクトディレクトリ総容量（原本複製・候補・探索履歴の寄与）が実用範囲か。
