# MVP 変更管理手順

本書は optpoet の MVP 境界・機能要件・受入条件を変更する際の正規手順である。変更が要件、テスト、
ロードマップの間で矛盾しないよう、更新順序と整合確認を固定する。関連文書は
[requirements.md](../requirements.md)、[quality-and-operations.md](../quality-and-operations.md)、
[architecture.md](../architecture.md)、[open-issues.md](open-issues.md)、
[ROADMAP](../roadmap/phase-0.md) を参照する。

## 適用範囲

以下のいずれかを変更する場合に本手順を適用する。

- MVP の対象・対象外（対象文字数、出力形式、フォント混在範囲を含む）
- 機能要件 `FR-NN` の追加・削除・意味変更
- 品質要件 `NFR-NN` の追加・削除・閾値変更
- 受入条件 `AC-NN` の追加・削除・判定基準変更
- 上記に連動するロードマップのタスクや完了ゲート

誤字修正、表現整理、リンク修正など要件の意味を変えない編集は本手順の対象外とし、通常の編集で足りる。

## 変更の起点

- すべての MVP 変更は、まず [open-issues.md](open-issues.md) に論点 `OI-NNN` として登録する。
- 状態を `決定` にしたエントリだけを本手順の入力とする。決定前の実装・テスト変更は行わない。
- 決定エントリには MVP 影響（`必須 / 望ましい / 対象外`）と決定日を必ず記録する。

## 更新順序

決定後、次の順序で更新する。順序を守り、各段でコミットを分ける。

1. **要件更新**: [requirements.md](../requirements.md) の該当 `FR-NN` / MVP 境界を更新する。品質・権利・
   検証に関わる場合は [quality-and-operations.md](../quality-and-operations.md) の `NFR-NN` / `AC-NN` も
   同時に更新する。ID は再利用せず、削除時も番号を欠番として残す。
2. **設計反映**: 実現方式に影響する場合は [architecture.md](../architecture.md) を更新する。
3. **テスト更新**: 追加・変更した `FR-NN` / `NFR-NN` / `AC-NN` に対応するテストを追加・修正する。
   受入記録テンプレート（P0-035）が存在する場合は対象項目を合わせて更新する。
4. **ロードマップ更新**: 影響するフェーズの `PN-NNN` タスクと完了ゲート `PN-GNN` を追加・修正する。
   タスクを不要化する場合は削除せず、取り消し線と理由を残す。
5. **来歴記録**: [open-issues.md](open-issues.md) の該当エントリへ、反映したファイルとコミット範囲を追記する。

## 整合確認

更新完了前に次を確認する。ひとつでも満たさない場合は変更を確定しない。

- `FR-NN` / `NFR-NN` / `AC-NN` の参照が全文書で一致し、宙に浮いた参照や重複 ID がない。
- 変更した要件に対応するテストが存在し、実行結果が記録されている。
- ロードマップのタスク・完了ゲートが変更後の要件を反映している。
- MVP 対象・対象外の記述が requirements.md 内で矛盾しない。
- 関連する未決事項エントリの状態と来歴が最新である。

## 役割

- 方針・境界の決定は Codex 側で行い、決定を open-issues.md に記録する。
- 決定済み方針の文書・テスト・ロードマップへの反映は実装側で行う。
- 整合確認は反映者が実施し、確認結果を来歴に残す。
