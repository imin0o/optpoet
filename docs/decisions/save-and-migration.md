# 原子的保存・読取専用オープン・スキーマ移行

**状態**: 定義済み（2026-07-25）。プロジェクト保存のコミット点と手順、クラッシュ時の回復規則、読取専用オープンの発動条件と挙動、将来のスキーマ移行方針を確定する。

**目的**: 「保存の途中でアプリや OS が落ちても、作者の直前の作業が壊れない」ことと、「アプリ版とプロジェクト版がずれても暗黙に壊さない」ことを、実装前に規則として固定する。

**対象タスク**: [P0-044](../roadmap/phase-0.md)

**関連**: [project-manifest.md](project-manifest.md) / [artifact-storage.md](artifact-storage.md) / [provenance-format.md](provenance-format.md) / [secret-exclusion-test.md](secret-exclusion-test.md) / [change-management.md](change-management.md) / [requirements.md](../requirements.md) / [quality-and-operations.md](../quality-and-operations.md)

## 原則

- 保存は「成功」か「何も変わっていない」かのどちらかにする。中間状態を残さない。失敗時に残るのは**直前の有効版**であり、書きかけの新版ではない（[quality-and-operations.md](../quality-and-operations.md) の異常系「保存容量不足」）。
- **正は `manifest.json`**。`index.sqlite` は manifest から再構築できる派生であり、その更新失敗は保存の失敗ではない（[artifact-storage.md](artifact-storage.md)）。
- 内容アドレスで置く実体は**不変**とする。同一ハッシュのファイルは同一内容なので、上書きが必要になる場面がない。保存は「実体の追記」と「manifest の 1 回の置換」に分解できる。
- **コミット点は `manifest.json` の置換 1 点のみ**。それ以前に落ちても、増えるのは参照されない実体（孤児）だけで、既存プロジェクトは無傷。
- 版の不一致は**暗黙に解決しない**。読めない版は明示エラー、読めるが書けない版は読取専用オープン、書けるようにするには明示的な移行操作を要求する。
- 移行はデータを作り直さない。実体（画像・AI 応答・出力）を書き換えず、manifest の構造だけを変換する。

## 1. 保存モデル

| 概念 | 定義 |
| --- | --- |
| 実体 | `input/` / `derived/` / `ai/` / `text/` / `outputs/` に置かれるファイル。内容アドレスまたは原本複製で、いったん確定したら書き換えない |
| 孤児 | ファイルシステム上に存在するが、現在の manifest から参照されない実体 |
| コミット点 | `manifest.json` の置換が成功した瞬間。ここより前の障害は「保存されなかった」、後は「保存された」 |
| 直前の有効版 | 置換前の manifest と、それが参照する実体の集合。実体は不変なので、manifest を 1 世代戻せば全体が戻る |

- 保存単位はプロジェクト全体ではない。新規実体を追記し、最後に manifest を 1 回置換する。既存実体は触らない。
- 同一ハッシュの実体が既にある場合は書込みを省略する。再計算・再保存の重複コストを避ける（[artifact-storage.md](artifact-storage.md) のキャッシュ再利用と同じ根拠）。
- 孤児は障害の証拠ではなく通常の残滓（中断した工程、破棄した候補）。**自動削除しない**。削除は明示操作とし、削除前に manifest の参照集合を全走査する。

## 2. 原子的保存の手順

保存要求ごとに A-01 から順に実行する。いずれかで失敗した場合、以降を実行せず `.tmp/` を破棄して中止する。

| 手順 | 内容 |
| --- | --- |
| A-01 | 新規実体を `.tmp/` へ書込む。`.tmp/` はプロジェクトルート直下に固定し、OS の一時ディレクトリを使わない（別ボリュームでは置換が原子的にならないため） |
| A-02 | 書込んだ実体を flush し、ファイル単位で fsync する |
| A-03 | 実体を最終パスへ置換移動する。内容アドレスのため衝突は同一内容を意味し、既存があれば移動を省略してよい |
| A-04 | manifest が参照する全実体が最終パスに存在し、ハッシュが一致することを確認する |
| A-05 | 新しい manifest を `.tmp/manifest.json` へ書込み、flush・fsync する |
| A-06 | `.tmp/manifest.json` に対して不変条件 I-01〜I-07（[project-manifest.md](project-manifest.md)）と層 A スキーマ検証（[secret-exclusion-test.md](secret-exclusion-test.md)）を実行する。失敗なら中止 |
| A-07 | 現行 `manifest.json` を `manifest.bak.json` へ置換移動する（1 世代のみ保持） |
| A-08 | `.tmp/manifest.json` を `manifest.json` へ**置換移動**する。**ここがコミット点** |
| A-09 | プロジェクトルートのディレクトリエントリを同期する（OS が対応する場合） |
| A-10 | `index.sqlite` を更新する。失敗しても保存は成功とし、索引を再構築可能として扱う |
| A-11 | `.tmp/` を空にする |

- A-06 を A-08 より前に置くのは、**検証に失敗した manifest を正の位置へ一度も置かない**ため。検証後に置換するので、`manifest.json` が不正な状態で存在する窓が生じない。
- 置換移動は同一ボリューム上の原子的置換 API を用いる（Windows では既存置換つきの移動、Python 標準では `os.replace`）。同一ボリュームであることは A-01 の `.tmp/` 配置で担保する。
- A-07 の `manifest.bak.json` は 1 世代のみ。実体は不変で残るため、manifest を 1 世代戻せば直前の作品状態が完全に復元できる。多世代の履歴は `index.sqlite` と来歴（[provenance-format.md](provenance-format.md)）の責務であり、バックアップの責務ではない。

## 3. クラッシュ時の状態と回復

| 障害時点 | ディスク上の状態 | 起動時の扱い |
| --- | --- | --- |
| R-01 A-01〜A-04 の途中 | 旧 manifest 健全、`.tmp/` に残留、孤児が増える可能性 | 旧版で通常オープン。`.tmp/` を破棄 |
| R-02 A-05〜A-06 の途中 | 旧 manifest 健全、`.tmp/manifest.json` が中途半端 | 旧版で通常オープン。`.tmp/` を破棄 |
| R-03 A-07 直後（A-08 前） | `manifest.json` 不在、`manifest.bak.json` 健全 | `manifest.bak.json` から復旧を提示（作者の明示操作で確定） |
| R-04 A-08 直後 | 新 manifest 健全、`.tmp/` に残留、`index.sqlite` が古い | 新版で通常オープン。`.tmp/` を破棄し、索引を再構築 |
| R-05 A-10 の途中 | 新 manifest 健全、`index.sqlite` が破損 | 新版で通常オープン。索引を manifest から再構築 |

- 起動時の判定順序: `manifest.json` が存在し検証を通れば通常オープン。存在しないか検証に失敗した場合のみ `manifest.bak.json` を評価し、健全ならば復旧を提示する。**自動で書き戻さない**（作者が新しい方を諦める判断をする）。
- `manifest.json` と `manifest.bak.json` の両方が検証に失敗した場合は、プロジェクトを開かず、実体が無傷であることと孤児からの手動復旧が可能であることを提示する。空の manifest を新規作成して上書きしない。
- `.tmp/` の残留物は起動時に破棄する（[artifact-storage.md](artifact-storage.md)）。破棄前に層 B の値パターン走査を実行し、秘密混入の残留を検査する（[secret-exclusion-test.md](secret-exclusion-test.md) の検査範囲）。
- 書込み失敗（容量不足、権限、ロック）は A-01〜A-05 のいずれかで検出され、中止して旧版が残る。**一時ファイルを最終成果として扱わない**（[quality-and-operations.md](../quality-and-operations.md)）。

## 4. 読取専用オープン

### 発動条件

| ID | 条件 |
| --- | --- |
| O-01 | 同一 MAJOR で `manifest.schema_version` の MINOR がアプリより新しい（[project-manifest.md](project-manifest.md) の読取規則） |
| O-02 | `manifest.bak.json` からの復旧を提示している最中 |
| O-03 | 検証で不整合を検出したが、参照実体が揃っており閲覧は可能 |
| O-04 | プロジェクトディレクトリが書込み不可（権限、読取専用媒体、別プロセスのロック） |

### 挙動

- 禁止: 保存、自動保存、編集操作（設定変更・意味編集・文章編集・候補選択・固定変更・素材追加）、AI 呼出、`index.sqlite` への書込み、`.tmp/` への書込み。
- 許可: 閲覧、保存済み応答からの再生（結果をプロジェクトへ書かない範囲）、エクスポート、未知項目を保持したままの複製。
- **未知項目は破棄せず保持する**（[project-manifest.md](project-manifest.md)）。複製も未知項目を保持したバイト等価のコピーとし、アプリが理解できる範囲へ再構成した保存を「複製」と称さない。
- 表示は理由と解除手段を必ず対にする。O-01 は「アプリを更新する」、O-02 は「復旧するか新しい方を採用するかを選ぶ」、O-03 は「不整合の内容と、複製してから修復する手順」、O-04 は「書込み可能な場所へ複製する」。「保存できません」だけを出さない。
- 異なる MAJOR は読取専用オープンではなく**明示エラー**とする。構造の意味が変わっているため、閲覧すら誤読になりうる。

## 5. スキーマ移行方針

### MINOR 移行

- 移行処理を持たない。読取側は未知の任意項目を保持し、欠落した任意項目は既定値で補う。
- 通常オープンで保存すると `manifest.schema_version` はアプリ側の MINOR で書かれる。読取専用オープン（O-01）では保存しないため、より新しい MINOR が切り下げられることはない。

### MAJOR 移行

| ID | 規則 |
| --- | --- |
| M-01 | 自動移行しない。作者の明示操作でのみ実行する |
| M-02 | 移行前に原本を複製し、複製に対して移行する。原本のディレクトリを書き換えない |
| M-03 | 移行器は N→N+1 の単段のみ実装する。複数版跨ぎは単段を連鎖適用する |
| M-04 | 移行は決定的とする。外部 AI を呼ばず、乱数・時刻・端末状態に依存しない |
| M-05 | 実体を書き換えない。移行対象は manifest の構造のみ。実体のハッシュは移行前後で一致する |
| M-06 | 移行後に不変条件を全数検証し、失敗した場合は移行結果を破棄して原本を残す |
| M-07 | ダウングレード（新版→旧版）は提供しない。旧版で開く必要がある場合は移行前の複製を使う |
| M-08 | 移行の事実を manifest へ記録する（`{from, to, tool_version}` の追記形式）。来歴（`edits`）へ混ぜない。作者の作品判断ではないため |

- M-08 の記録欄は `manifest` ブロックへの任意項目の追加であり、MINOR 追加として扱う。正式な項目名と位置は [project-manifest.md](project-manifest.md) を `1.x` で更新して確定する（[change-management.md](change-management.md) の手順）。
- 各 MAJOR について、移行前の fixture プロジェクトを検証データとして保持する。移行器の回帰テストは fixture → 移行 → 不変条件検証 → 再生結果の一致（AC-04）で行う。
- MAJOR を上げる判断そのものは [change-management.md](change-management.md) に従い、要件・テスト・ロードマップを同時に更新する。

## 6. 保存の実行タイミング

- 明示保存（作者操作）と自動保存（工程完了時）の双方が同じ A-01〜A-11 を通る。自動保存だけ手順を省略しない。
- 長時間工程の中断・再開（NFR-05）は、工程完了時の自動保存でコミット点を刻むことで成立する。中断はコミット済みの地点まで戻る。
- fsync（A-02 / A-05）は保存時間に効く。実体の fsync と manifest の fsync は省略しない。`index.sqlite`（A-10）は同期を要求しない。
- 保存時に走る検証は層 A のみ（A-06）。層 B の全走査はエクスポート時と開発時テストに限る（[secret-exclusion-test.md](secret-exclusion-test.md)）。

## 再確認事項（実装時に更新）

- 参照環境の割当ドライブ（`Z:` 等）およびネットワークドライブ上で、置換移動が原子的に振る舞うか。原子的でない場合、プロジェクトの配置先を制限するか手順を変える必要がある。
- ウイルス対策ソフトによる一時的なファイルロックで置換移動が失敗する頻度と、再試行回数・間隔の妥当性。
- SQLite の WAL ファイル（`index.sqlite-wal` / `-shm`）が A-11 の `.tmp/` 掃除および孤児判定と干渉しないか。
- A-02 / A-05 の fsync が 2,000 セル・5,000 セル規模の保存で NFR-04 の目標時間を圧迫しないか。
- `manifest.bak.json` 1 世代で、作者が実際に戻したい地点をカバーできるか（連続自動保存で有効な退避が押し流されないか）。
- 読取専用オープン中の「再生」が、プロジェクトへ一切書込まずに完了できるか（キャッシュ書込みの経路が残っていないか）。
